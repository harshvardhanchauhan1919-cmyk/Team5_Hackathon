## 0. What changed from v1

- **Team reality:** no professional coders → **AI writes the code, the team directs and verifies it.** Architecture stays real, but scope is MVP-first.
- **Hero story over completeness:** the win condition is showing a **break → diagnose → repair → re-run** loop working live, on a site we control.
- **Demo site is generated by us**, with deliberate "break toggles."
- **Models via OpenRouter**, tiered to stretch limited credits, switchable by config.
- **Self-healing covers selectors, timeouts, AND flow/logic changes.**
- **Regression Monitor:** designed into the architecture from day one, built only if the core is solid.

## 1. Pitch

Browser automation breaks when the UI changes. We turn it into a **self-healing system**: when a run fails, the system diagnoses *why* and repairs its own script — including adapting to changed flows — then re-runs, with no human debugging.

## 2. Win condition (hackathon)

The judge clones the repo, reads clean code, and watches a video where:
1. An automated flow runs successfully on our demo site.
2. We flip a "break toggle" (rename a button / move an element / change a step).
3. The run fails → the system explains the failure → repairs the script → re-runs → passes.
4. A simple, good-looking UI shows the agent pipeline doing this, with screenshots.

Everything in this PRD serves that four-beat story.

## 3. Success metrics

| Metric | Target (rehearsed demo) |
|---|---|
| Auto-repair success rate (the hero metric) | ≥ 50% of injected failures |
| Failure classes healed | selector, timeout, missing element, + ≥1 flow/logic change |
| Demo reliability | 100% on rehearsed scenarios |
| Code review impression | small files, typed, documented, one clear entry point |

## 4. Architecture (LangGraph)

Agents are nodes; the flow is explicit edges; the **repair path is a cycle**.

```
Flow Discovery → Script Generator → Execution ──► pass ──► Report/UI
                                        │
                                     fail
                                        ▼
                                Error Diagnosis → Adaptive Repair ──► re-run Execution
                                        │                                 │
                                        └──── give up after N attempts ◄───┘
   Regression Monitor (bonus): diffs new screenshots vs a stored baseline
```

**Two layers, kept strictly separate:**
- **Reasoning (LLM):** Discovery, Diagnosis, Repair — the parts that need adaptation.
- **Tools (deterministic Playwright):** the actual browser actions.
- Rule of thumb: deterministic DOM actions for the predictable ~80%; LLM only where the page has genuinely changed. Cheaper, faster, easier to demo and review.

**Agents**
- **Flow Discovery** — identifies flows to automate (login, signup, checkout). *For the demo, keep light: our own site means we can seed/hint the flows rather than fully auto-discover.*
- **Script Generator** — writes a Playwright script for a flow.
- **Execution** — runs the script; captures result + screenshots/video/trace.
- **Error Diagnosis** — classifies + explains the failure (selector / timeout / missing element / changed flow).
- **Adaptive Repair** — rewrites the script to fix it, re-runs, up to N attempts.
- **Regression Monitor (bonus)** — visual diff vs baseline.

## 5. Shared contract (build FIRST, freeze it)

Typed state so agents can be built in parallel against mocks.

```python
Flow(id, name, steps: list[Step], target_url)
Step(action, selector, value, description)
Script(flow_id, code: str)
RunResult(script_id, status, logs, screenshots, video, trace, error: Error | None)
Error(kind: Literal["selector","timeout","missing_element","flow_change"], message, step_index)
Diagnosis(error, root_cause, confidence, suggested_fix)
RepairAttempt(diagnosis, new_script, attempt_no, result: RunResult | None)
```
Every agent is a node: `def node(state) -> state`.

## 6. Model configuration (OpenRouter, tiered)

One endpoint, one key, switch by string. Never hardcode a model.

`.env`
```
OPENROUTER_API_KEY=sk-or-...
OPENROUTER_BASE_URL=https://openrouter.ai/api/v1
```

`models.yaml` — map *roles* to models, so we tune cost per agent:
```yaml
discovery:   deepseek/deepseek-v4-flash      # cheap workhorse
script_gen:  qwen3-coder                     # cheap, strong at code
execution:   none                            # deterministic, no LLM
diagnosis:   anthropic/claude-sonnet-4.6     # reasoning tier
repair:      anthropic/claude-sonnet-4.6     # reasoning tier
dev_default: <model>:free                    # free tier for building only
```

Wiring (OpenRouter is OpenAI-compatible):
```python
from langchain_openai import ChatOpenAI
def model_for(role):
    return ChatOpenAI(model=CFG[role], base_url=OPENROUTER_BASE_URL,
                      api_key=OPENROUTER_API_KEY, temperature=0)
```

Rules:
- **Reasoning tier only for Diagnosis + Repair.** Everything else on the cheap tier.
- **`:free` models for dev/testing only** — rate-limited and the lineup rotates; never in the recorded demo.
- If an agent is flaky on **tool calls**, bump *that role* up a tier, don't switch globally.
- Keep system prompts stable to benefit from prompt caching → lower cost.

## 7. Team & the no-code reality

| Who | Owns |

## 8. Demo site (we generate it)

A small self-contained app we fully control — the reliability backbone of the demo.
- Pages: login, signup, a multi-field form, product list, checkout.
- **Break toggles** (env var or `?break=` param) that: rename a button, change a selector/id, move an element, add a delay (→ timeout), or reorder a step (→ flow/logic change).
- Ship it in the repo; run it in the same Docker compose as the agent so a judge gets the whole thing with one command.
- QA owns this; it doubles as the fixture set for automated tests.

## 9. Dev workflow

- **Repo:** monorepo, one package — `schemas / graph / agents / tools / ui / harness / tests / fixtures / demo_site`.
- **Deps:** uv.
- **Branching:** trunk-based, tiny PRs into `main`, one review + green CI. Stubs/flags keep `main` demoable always. Small reviewed PRs = the "clean code" score.
- **Testing:** unit-test each node with the **LLM mocked** and Playwright against the **local demo site** (deterministic). Keep nondeterministic LLM calls out of CI.
- **Harness / scoreboard:** a runner over `{flow, break_toggle}` cases that executes the pipeline, records auto-repair success + screenshots, and prints the metrics table. This is your test rig, your scoreboard, and your demo backbone in one.
- **CI:** GitHub Actions — ruff (lint+format), mocked-LLM unit tests, `playwright install`. Keep < ~2 min.
- **Deploy:** `docker compose up` runs demo site + agent + UI. No cloud needed; a clean local run scores "easily testable." Playwright's official image ships the browsers.

## 10. 16-hour plan (protect the buffer)

| Hours | Goal |
|---|---|
| 0–1 | Setup: repo, uv, OpenRouter key, AI coding tool installed for everyone, "hello browser" runs, **freeze the schema (§5)** |
| 1–3 | Parallel: QA builds demo site + break toggles · AI-build wires the **walking skeleton** (6 stub agents in LangGraph, UI shows a run) |

| 7–11 | **Hero loop:** Diagnosis → Repair → re-run. Flip a toggle, watch it heal. Do selector + timeout first, then one flow/logic change |
| 11–14 | Polish: good-looking UI, harness/scoreboard + metrics, more break cases. Regression Monitor **only if ahead** |
| 14–15 | **Feature freeze.** Record the video, write the README, clean the code |
| 15–16 | Buffer: rehearse, fix demo flakiness, breathe |

**Hard rule: stop building new features at hour 14.** A working four-beat demo beats a half-built sixth agent every time.

## 11. Risks

- **Over-scope** → MVP-first; Regression Monitor is bonus; feature-freeze at H14.
- **LLM nondeterminism breaks the demo** → temperature 0, rehearse fixed scenarios, deterministic fallbacks, don't use free models in the video.
- **No-coder debugging stalls** → keep files tiny so the AI tool can regenerate a whole file cleanly; verify by running, not by reading alone.
- **Credit burn** → cheap tier by default, free models in dev, reasoning tier only for Diagnosis/Repair.
- **Integration crunch** → walking skeleton early, frequent tiny merges, PM owns `main`.
